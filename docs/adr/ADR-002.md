# ADR-002: PostgreSQL + EF Core (Npgsql) as the only store, with the EF InMemory provider for unit tests

## Status

Accepted (in the code)

## Date

2026-11-27

## Context

The API is fundamentally a state machine over `SongMetadata` rows (see [ADR-003]); correctness
depends on relational features: global query filters for tenancy, Postgres triggers that maintain
row-version stamps, soft-delete columns, and parameterized per-user filters in a shared compiled
model. The test suite must run on every PR (CI is a required check) without provisioning a
database, but some behavior — notably the row-version triggers — only exists in real Postgres.

## Decision

- **Production store:** PostgreSQL via Npgsql EF Core. `Program.cs` registers the context
  explicitly (non-pooled, so a second constructor taking `ICurrentUserAccessor` can drive
  per-user global query filters) and calls `UseNpgsql(..., npgsql => npgsql.EnableRetryOnFailure())`
  ([MusicHoarder.Api/Program.cs]). All schema changes go through EF migrations under
  `MusicHoarder.Api/Persistence/Migrations/`; `ApplyPendingMigrationsAsync()` runs at startup, so
  no manual SQL ships ([`AGENTS.md`](../../AGENTS.md), "Persistence").
- **Unit tests:** xUnit with `Microsoft.EntityFrameworkCore.InMemory`
  ([MusicHoarder.Api.Tests/MusicHoarder.Api.Tests.csproj]) — "no Postgres/Docker required"
  ([`AGENTS.md`](../../AGENTS.md), Commands). Fixtures build the context with `UseInMemoryDatabase`, so the full
  suite runs locally and in CI in seconds.
- **Postgres-specific behavior is tested against real Postgres, but only where it exists:**
  `RowVersionTests` run against Postgres in CI and are skipped locally without
  `MUSICHOARDER_TEST_POSTGRES` ([`AGENTS.md`](../../AGENTS.md), "Persistence"). The InMemory provider is never
  claimed to validate trigger or SQL semantics.

## Options considered

| Dimension                      | PostgreSQL + EF Core (Npgsql)                      | SQLite for prod                                    | MongoDB / document store                       |
| ------------------------------ | -------------------------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| Global query filters (tenancy) | First-class, parameterized per query               | Supported, but weaker relational features          | Hand-rolled per query                          |
| Row-version triggers           | Native triggers, used by `Persistence/RowVersions.cs` | No server-side triggers                          | Manual bookkeeping                             |
| JSON/metadata columns          | JSONB available                                    | JSON functions weaker                              | Native, but no joins/constraints               |
| Test speed without Docker      | InMemory provider for units; real PG for trigger tests | Same engine locally and in prod (simpler parity) | Emulator/separate server needed                |
| Operational cost for self-hosters | One well-known container; documented in [SELF_HOSTING.md] | Lower, but a downgrade in features          | Extra service to host                          |
| Migration story                | EF migrations applied at startup                   | Same mechanism                                     | Schemaless / hand scripts                      |

For the test provider specifically:

| Dimension          | EF InMemory provider                          | Testcontainers (real Postgres per test run)     | SQLite provider in tests                       |
| ------------------ | --------------------------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| Run cost           | None — in process, no Docker                  | Docker required locally; slower CI              | Fast, but different SQL dialect                |
| Fidelity to prod   | Low (no transactions, triggers, relational ops) | Highest                                       | Medium                                         |
| Where the gap is closed | CI-only Postgres tests for trigger semantics | —                                          | Still not the prod dialect                     |

## Trade-off analysis

- **Gained:** fast, hermetic unit tests (a hard requirement for a suite this size — the test tree
  mirrors ~40 source folders); a single relational model that already expresses tenancy via
  shared compiled-model filters; startup migration application makes every environment
  self-upgrading.
- **Paid:** the InMemory provider can pass code that Postgres would reject (raw SQL, triggers,
  collation). The repo knows this and compensates: Postgres-gated tests for row versions, and a
  documented rule that a context made in a test "stores the plain value" for encrypted
  `ProtectedStringConverter` columns — such behavior "check[s] the stored text against Postgres"
  ([`AGENTS.md`](../../AGENTS.md), "Persistence").
- **Paid (operational):** self-hosters run a second container; the pinning of Postgres 17.6 in
  [ADR-001](ADR-001.md) exists precisely because an unpinned image could upgrade the live database.

## Consequences

- `ConnectionStrings__musichoarderdb` is the one connection string; Aspire injects it in dev
  ([`AGENTS.md`](../../AGENTS.md), "Configuration").
- New schema work is always a migration; tests that need relational semantics must either be
  rewritten as pure logic tests or added to the Postgres-gated set.
- `ListVersion`/`NameVersion` trigger semantics and the `DetectColumns` projection discipline are
  the known places where InMemory tests are insufficient; see [`AGENTS.md`](../../AGENTS.md) "Persistence" before
  trusting an InMemory-only green run in those areas.
