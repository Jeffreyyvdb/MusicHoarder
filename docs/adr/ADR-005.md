# ADR-005: One weekly semantic-release cut for the whole repo, with deployment decoupled as `:edge` builds

## Status

Accepted (in the code)

## Date

2026-11-27

## Context

The repo ships multiple deployables from one codebase: the .NET API, the SvelteKit frontend, and
the Capacitor app shell ([ADR-006]). Release tags must apply to all of them at once, versions
must come from commit history rather than hand-edited manifests, and — measured in practice —
releasing on every merge was unsustainable: it cut 15 versions in one day, which meant 15
release notifications, 15 moves of `:latest` for anyone auto-updating, and a Google Play build
per merge (recorded in the header comment of [.github/workflows/release.yml]).

At the same time, the maintainer's own instance needs fixes live immediately; a weekly release
train must not delay deployment.

## Decision

- **One shared version line.** The whole repo is versioned by
  [semantic-release](https://github.com/semantic-release/semantic-release) as a single
  `v${version}` tag covering API **and** frontend ([frontend/.releaserc], `tagFormat:
  "v${version}"`). Commit messages follow Conventional Commits and are load-bearing on *every*
  commit (`fix:` → patch, `feat:` → minor, `feat!:`/`BREAKING CHANGE:` → major, `chore:`/`docs:`/
  `refactor:`/`test:`/`style:` → no release) — [AGENTS.md], "Branches and commits".
- **Releases are weekly, deploys are per-push.** `.github/workflows/release.yml` runs Mondays
  07:00 UTC (or manually for urgent fixes), gates on frontend `check`+`lint`+`build` **and**
  `dotnet test`, then cuts at most one GitHub Release. The Releases page is the canonical
  changelog; `frontend/CHANGELOG.md` is a stub pointing at it. Every push to `main`
  separately runs `aspire-deploy.yml`, which builds `:edge`/`:sha-<commit>` images and redeploys
  the maintainer's Dokploy instance — so nothing waits a week to go live.
- **On release, `release.yml` dispatches `aspire-deploy.yml`** with the new version to build and
  semver-tag images (`:X.Y.Z`, `:X.Y`, `:X`, `:latest`) without redeploying; it also builds the
  Android app shell and uploads the bundle to Google Play, both best-effort so an Android
  breakage never holds back the API/frontend release.
- **No release commit is pushed back to `main`.** Following the semantic-release maintainers'
  FAQ, `@semantic-release/git` and `@semantic-release/changelog` are not used; the downstream
  build is triggered with `gh workflow run` (`workflow_dispatch`), the one event the default
  `GITHUB_TOKEN` may fire — so no PAT is needed and `main`'s branch-protection rules need no
  bypass actor.

## Options considered

| Dimension                     | Weekly unified semantic-release (chosen)     | Release per push, unified                     | Per-project versioning (api-v*, frontend-v*)   | Manual version bumps                              |
| ----------------------------- | -------------------------------------------- | --------------------------------------------- | ---------------------------------------------- | ------------------------------------------------- |
| Versions per week             | ≤ 1                                          | ~15 observed in one day                       | Many, per project                              | Unpredictable                                     |
| Changelog authorship          | From Conventional Commits                    | Same                                          | Same, but split                                | Hand-written, often skipped                       |
| `:latest` stability for self-hosters | Moves at most weekly                  | Constant churn                                | Two tags to track                              | Stale                                             |
| App-store build frequency     | Weekly (fits store review)                   | Per merge (unreviewed changes shipped weekly regardless — Play track is `internal`) | Per merge per store | Manual |
| Drift between API/frontend versions | Impossible — one tag                   | Impossible                                    | Real risk (paired features span projects)      | Real risk                                         |
| Complexity                    | One workflow, one tag format, manual dispatch for hotfixes | Requires release cooldown hacks         | Two release configs, two tag schemes           | None, but no automation                           |

## Trade-off analysis

- **Gained:** deterministic versions derived from commit history; a single changelog covering
  paired API+frontend features; predictable `:latest` for self-hosters; hotfixes still available
  via manual workflow dispatch.
- **Paid:** a merged fix can wait up to a week to appear in a *release* (mitigated: the
  maintainer instance runs `:edge` immediately, and urgent fixes release on demand).
  Every commit message must be convention-conforming, including bot PRs — Dependabot config
  reflects this deliberately: bun dependency PRs use `fix(deps)` (cut a patch release, on
  purpose), NuGet bumps use `chore(deps)` so routine .NET bumps never cut a release.
- **Paid (edge versioning):** an edge build's API version reads `<last release>-edge.g<sha>`
  rather than a plain number, precisely so it cannot compare as older than a release cut from the
  same commit; the update check then asks GitHub's compare API before showing a banner.

## Consequences

- Contributors must write Conventional Commits; the `v1.9.1` bridge tag continues the line from
  the retired `frontend-v*` tags, and `frontend/package.json`'s `version` field is intentionally
  stale.
- semantic-release v25+ needs Node ≥ 22.14, so CI installs Node 24 alongside Bun and invokes
  `npx semantic-release` for that one step (Bun's Node-compat layer reports 20.x).
