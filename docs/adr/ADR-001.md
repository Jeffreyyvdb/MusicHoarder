# ADR-001: Use .NET Aspire as the single source for both local orchestration and deployment artifacts

## Status

Accepted (in the code)

## Date

2026-11-27

## Context

MusicHoarder runs at least three cooperating processes in every environment: the ASP.NET Core API
(`MusicHoarder.Api`), the SvelteKit frontend (`frontend/`), and a PostgreSQL database whose schema
is managed by EF Core migrations. Secrets and paths (music source/destination directories, AcoustID
and Spotify keys, OAuth relay settings, email credentials) differ per environment. The maintainer
runs the same stack locally, in PR previews, on a production Docker Swarm host, and as a
self-hosting template that strangers deploy to Dokploy.

Maintaining a hand-written `docker-compose.yml` for each of these shapes would guarantee drift:
the local dev experience (per-branch database volumes, dashboard prompting for missing secrets)
has no equivalent in a plain compose file, and the compose file would silently diverge from the
values the API actually reads.

## Decision

The `MusicHoarder.AppHost` project ([MusicHoarder.AppHost/AppHost.cs]) is the single source of
truth. `dotnet run --project MusicHoarder.AppHost` runs the full local stack — provisioning
PostgreSQL as a persistent container with a named data volume, applying EF migrations on API
startup, and starting the frontend as a Bun-run Vite app (`AddViteApp(...).WithBun()`) pointed at
the API. Every required path/secret is modeled with `AddParameter(...)` (secrets flagged
`secret: true`), injected into the API as double-underscore environment variables
(`MusicEnricher__SourceDirectory`, `Spotify__ClientSecret`, …), and prompted for in the Aspire
dashboard on first run.

The same AppHost also emits the deployment artifacts: `builder.AddDockerComposeEnvironment("compose")`
makes `aspire publish` produce compose output, shaped per target by `DEPLOY_TARGET`
(swarm for production, `compose` for previews, `selfhost` for the published template —
[MusicHoarder.AppHost/ComposeFileExtensions.cs]). Images go to GHCR via
`AddContainerRegistry("ghcr", "ghcr.io", "jeffreyyvdb/musichoarder")` and CI sets `MH_IMAGE_TAG`
(`edge` on push to main, the release version on a release). CI (`aspire-deploy.yml`) builds
`:edge` images and redeploys the maintainer's Dokploy instance on every push to `main`.

## Options considered

| Dimension                  | .NET Aspire AppHost                            | Hand-maintained docker-compose + scripts      | Plain `dotnet run` + shell scripts (no orchestrator) |
| -------------------------- | ---------------------------------------------- | --------------------------------------------- | ---------------------------------------------------- |
| Local dev boot             | One command; dashboard prompts for secrets     | Requires `.env` discipline; errors at runtime | Manual multi-terminal setup                          |
| Secret handling            | Typed parameters, user-secrets, dashboard UI   | `.env` files, easy to commit by accident      | Per-shell exports, no prompting                      |
| Migration on startup       | Wired once in the API (`ApplyPendingMigrationsAsync`) | Extra container/step per shape         | Manual                                               |
| Multiple deploy shapes     | One model, `DEPLOY_TARGET` switch              | N parallel compose files that drift           | N scripts that drift                                 |
| Service discovery/refs     | `WithReference` wires connection strings       | Manual env-var plumbing                       | Manual                                               |
| Cost / learning curve      | New framework, experimental APIs (`ASPIRE*` suppressions in code) | Familiar, low tooling risk | Lowest                                              |
| Debuggability of the graph | Dashboard with logs/traces/endpoints per resource | Logs only                                  | Logs only                                            |

## Trade-off analysis

- **Gained:** one place to change wiring; dev, preview, prod and self-host compose all generated
  from the same resource graph; per-branch database volumes derived from the AppHost directory
  (`musichoarder-volume-<key>`) so worktree migration histories never collide; intentional
  hardening captured once — e.g. the Postgres image is pinned to `17.6` with a comment explaining
  that an unpinned tag would silently propose a major-version upgrade and volume-path change to
  the live database ([MusicHoarder.AppHost/AppHost.cs], "Pin the Postgres image" block).
- **Paid:** dependence on Aspire's experimental APIs — the AppHost carries several
  `#pragma warning disable ASPIRECOMPUTE003 / ASPIREPIPELINES003 / ASPIREJAVASCRIPT001`
  suppressions and a workaround comment where retries are set manually because the Aspire
  integration's retry setup throws with Npgsql EF 11 ([MusicHoarder.Api/Program.cs], lines ~45–54).
  Version upgrades of Aspire are a real maintenance surface (see `aspire.config.json`, SDK 17.0.0).
- **Mitigation:** the generated output (`docker-compose.yml` at the repo root, committed) is
  reviewable, and the deploy shapes are covered by CI actually publishing them.

## Consequences

- Developers need Docker running before starting the AppHost (Postgres is a container).
- First-run secrets live in the AppHost's user-secrets store under `Parameters:*` keys, per
  [AGENTS.md] — never in tracked files.
- The Aspire dashboard itself is deliberately **not** deployed: the compose environment sets
  `DashboardEnabled = false` and the prod stack sends OTLP to the host's own collector
  ([MusicHoarder.AppHost/AppHost.cs]).
- See [SELF_HOSTING.md](../SELF_HOSTING.md) for the operator-facing flow that consumes the
  self-host compose shape.
