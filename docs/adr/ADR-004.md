# ADR-004: Activity and job reporting are derived at read time, not written to event-log tables

## Status

Accepted (in the code)

## Date

2026-11-27

## Context

Users ask "what has this thing been doing?" — the History feed (`GET /api/history`), the Pipeline
page's per-job charts (`GET /api/background-work`), and song provenance (`GET
/api/songs/provenance`) all answer it. The obvious implementation is an event log written inside
every background service. But that approach has known failure modes here: the pipeline already
has ~20 `BackgroundService`s ([ADR-003]); a write in each of their hot paths would slow every
sweep; and any event log is incomplete for rows that predate the feature.

## Decision

Derived views, not event logs. The History feed **derives** its entries at read time from rows
the pipeline already writes (a `WishlistItem`'s status, a song's `LyricsSyncCheckedAtUtc`, an
`UpgradeRequest`'s completion, two `EnrichmentSnapshot`s disagreeing about the config hash).
Background work reporting works the same way: one `IBackgroundJobInsight` per job id in
`BackgroundJobIds` ([MusicHoarder.Api/BackgroundWork/BackgroundJobInsight.cs], implementations in
`BackgroundWork/Insights/`) builds each job's summary row and chart panels from existing rows at
request time — there is no `BackgroundWork` table and no event log. Provenance
([MusicHoarder.Api/Library/SongProvenance.cs]) likewise re-derives "why is this track in the
library", including recomputing which owned tracks an album fill started from.

Two structural rules keep these derived views honest ([AGENTS.md], "Background work"):

1. A queue is counted with the **same named predicate the sweep takes songs from**
   (`LyricsTimingQueries.WhereDueFor…`, `CoverArtSweepRules`, `QualityGradingQueries.WhereGradeable`,
   `EnrichmentQueries.WhereRetryableProviderAttempts`, `MusicVideoPrefetchScope`) — never a copy
   of its `Where` chain — so when a sweep's selection changes, the chart cannot silently drift.
2. Live state that rows cannot express (what a service is doing *this minute*) is reported to the
   in-process singleton `BackgroundWorkStatus` (working / idle until / waiting with a reason /
   failing with the exception *type*), never to a table. The same summaries are exported as
   OpenTelemetry gauges (`BackgroundWorkMetrics`, tagged `background_job`) for Grafana.

The one exception the code makes: `LibraryWriteEvent` **is** an append-only log, because a tag
diff is unrecoverable after the fact — derived views are for facts that the rows still show.

## Options considered

| Dimension                        | Derived at read time                       | Append-only event log table                    | Hybrid (log + projections)                    |
| -------------------------------- | ------------------------------------------ | ---------------------------------------------- | --------------------------------------------- |
| Correct for pre-feature rows     | Yes — computed from current state          | No — history starts at the feature             | No for the logged part                        |
| Hot-path cost                    | Zero extra writes                          | One insert per event, per job                  | One insert per event                          |
| Read cost                        | Grows with library; mitigated by memos     | Cheap indexed reads                            | Cheap                                         |
| Audit fidelity ("what changed")  | Cannot recover past values                 | Full                                           | Full                                          |
| Consistency with sweep selection | Guaranteed if the shared predicates are used | Drifts when the sweep and the log disagree    | Drifts likewise                               |
| Schema/migration cost            | None                                       | Table + retention policy per event kind        | Both                                          |

Read-cost mitigations in the code: `DetectionCountMemo` remembers duplicate counts under a
content stamp, inbox name counts are stamped with Postgres `ListVersion`/`NameVersion` row
versions so steady-state polls skip recomputation, and a collection refresh snapshot is
regenerated at most every 5 minutes in the background.

## Trade-off analysis

- **Gained:** no write cost on ~20 background sweeps; every new event kind automatically covers
  historical rows; charts cannot drift from the sweeps they describe because they *are* the sweep
  predicates; no retention/cleanup jobs.
- **Paid:** [AGENTS.md] states the limit plainly — these are "last time X happened" stamps, so
  the feed is an **activity view, not an audit log**; read cost grows with library size and must
  be memoized; a fact that leaves no durable trace (e.g. which music-video candidate was
  rejected) can only be reported as an outcome, not a narration.
- **Accepted exception:** `LibraryWriteEvent` exists exactly for the one thing rows cannot
  reconstruct (the before/after of a tag write).

## Consequences

- To surface a new kind of event, add an `IActivitySource` — not a table, not a write inside a
  background service.
- To report on a new background job: add its id to `BackgroundJobIds`, write an
  `IBackgroundJobInsight`, register it in `AddBackgroundWork`, and have the service report to
  `BackgroundWorkStatus` (a test fails on a missing or doubled id).
- The insight contract mirrors `frontend/src/lib/background-work/types.ts` — change both together.
- Never reuse a copy of a sweep's `Where` chain in a chart; extract it into the shared named
  predicate.
