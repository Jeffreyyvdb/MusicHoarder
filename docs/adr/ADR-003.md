# ADR-003: The ingestion pipeline is a set of independent BackgroundServices sweeping a `SongMetadata` state machine

## Status

Accepted (in the code)

## Date

2026-11-27

## Context

Getting one song from "a file on a NAS share" to "a tagged copy in the destination library"
involves scanning, fingerprinting (fpcalc/AcoustID), multi-provider metadata enrichment
(AcoustID, MusicBrainz, Spotify, community trackers), duplicate detection, lyrics, cover art and
finally copying/tagging. Each stage is slow, IO-heavy, externally rate-limited, and can fail
independently. The work must survive restarts, proceed without a user driving it, and let an
admin trigger, pause or re-run individual stages.

## Decision

Each stage is a `BackgroundService` that periodically sweeps the database for rows in the status
it handles — there is no in-memory job scheduler or external queue. The state lives on
`SongMetadata` ([MusicHoarder.Api/Persistence/SongMetadata.cs]) as status enums that are the
contract between stages:

```
Scanner → Fingerprint → Enrichment (multi-provider) → Duplicate detection → LibraryBuilder
```

- `EnrichmentStatus`: `Pending → Matched | NeedsReview | Failed`
- `LibraryBuildStatus`: `Pending → Copied → Tagged → Done` (or `Failed`)
- `LyricsStatus`: `NotFetched → Fetched | Instrumental | NotFound | Failed`

Readiness between stages is expressed as computed properties (`IsReadyForEnrichment`,
`IsReadyForBuild`, `IsReadyForLyricsFetch`) rather than predicates duplicated into queries.
Services are registered with `AddHostedService<T>()` in
[MusicHoarder.Api/Composition/ServiceCollectionExtensions.cs] (~20 hosted services: scanner,
fingerprint, enrichment, library builder, download, music-video, album completion, artist
monitor, quality grading, sync services, and more). Cross-cutting concurrency uses
`SemaphoreSlim` with limits from configuration (`SmbConcurrency`, `FingerprintConcurrency`,
`EnrichmentWorkerConcurrency`, …) and channels for decoupling HTTP requests from heavy work —
e.g. `EnrichmentOrchestrator` / `EnrichmentPipelineChannel` and the `Channel<Guid>` queues inside
`JobManager` ([MusicHoarder.Api/Jobs/JobManager.cs]).

A thread-safe singleton `JobManager` enforces **one job at a time per step**: steps are
independent and run concurrently (a Build does not block a Scan), and `/api/enrichment/*`
trigger endpoints return `409 Conflict` only when *that same step* is already running. Progress
is streamed to the frontend via SSE under `/api/enrichment/*`.

## Options considered

| Dimension                       | DB-sweeping BackgroundServices                 | In-memory work queue (Channels only)           | External queue (RabbitMQ/Redis) + workers       |
| ------------------------------- | ---------------------------------------------- | ---------------------------------------------- | ------------------------------------------------ |
| Durability across restarts      | High — state is the DB row                     | Low — queued items lost on restart             | High, if queue is persistent                     |
| Survives crashes mid-stage      | Yes; row stays in its status                   | Needs replay logic                             | Redelivery, but out-of-order risk                |
| Self-host operational cost      | None — the DB is already there                 | None                                           | Extra service every self-hoster must run         |
| Backpressure / rate limiting    | Sweep interval + `SemaphoreSlim` from config   | Bounded channels                               | Queue-level, but external                        |
| Observability                   | Rows *are* the audit state; feeds [ADR-004]    | Needs separate logging                         | Queue dashboards                                 |
| Complexity                      | Low, uniform across ~20 services               | Medium                                         | High (broker deployment, serialization versions) |
| Latency for a single new song   | Sweep interval (seconds–minutes)               | Immediate                                      | Immediate                                        |

The latency cost is accepted: the product is a background library builder, not an interactive
importer, and `AutoScanBackgroundService` re-scans every
`MusicEnricher:AutoScanIntervalMinutes` (default 15) with a `ScanSettleSeconds` guard so a scan
landing mid-copy does not index half-written files.

## Trade-off analysis

- **Gained:** crash-safe (state always in Postgres), trivially observable (any client can read
  the statuses; progress singletons like `ScanProgressTracker` and the `/api/background-work`
  insights derive from the same rows), zero extra infrastructure for self-hosters, and a uniform
  pattern a new contributor can copy from any existing stage.
- **Paid:** polling sweeps cost queries on a timer; a stage's latency is bounded below by its
  sweep interval; ordering guarantees between stages are implicit in the status enums rather than
  enforced by a scheduler.
- **Deliberate sharp edges recorded in [AGENTS.md]:** `JobManager.TryStartJob` deliberately
  *clears* the pause flag (it models a user action), so any new auto-trigger must check
  `IsStepPaused` first; per-song enrichment can leave album-identity tags inconsistent, which is
  repaired at build time by `AlbumIdentityReconciler` rather than by persisting a canonical
  album per track.

## Consequences

- New pipeline features should follow the pattern: a status enum, readiness gates as computed
  properties, a `BackgroundService` sweep, concurrency from options, and registration in
  `AddMusicHoarderServices()`.
- Never physically delete rows — `SoftDelete()` sets `DeletedAtUtc`; `IsDeleted` is derived.
- Reporting a new job to the Pipeline page is a separate, standardized step — see [ADR-004].
