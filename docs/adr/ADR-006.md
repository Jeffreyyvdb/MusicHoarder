# ADR-006: One SvelteKit web client served by adapter-node in Docker, plus a thin Capacitor shell — no second client codebase

## Status

Accepted (in the code)

## Date

2026-11-27

## Context

MusicHoarder must be usable on desktop browsers, on phones, and in an installed-app shape for
app stores. The obvious native route — separate iOS and Android clients — had already been
tried: until November 2026 there was a native Android client in `android/`, a line-by-line
Compose port of the web's library modules. It was retired because "keeping two copies of every
rule in step kept failing" ([AGENTS.md], "One client, and the app shell around it"): album
grouping rules implemented twice produced the same bug twice (PR #453) and had drifted in six
ways before the rules were moved to the server.

Meanwhile the web client must run as a real server-side process (it proxies API calls same-origin
to avoid CORS, sets security headers, compresses JSON responses, and server-renders share pages
for link-preview crawlers), so a purely static SPA deployment is not an option either.

## Decision

Two layers, one client:

1. **The web app is the only client.** `frontend/` is a SvelteKit 3 + Svelte 5 (runes) app built
   with `@sveltejs/adapter-node` (`adapter: adapter()` in [frontend/vite.config.ts] — there is no
   `svelte.config.js`; SvelteKit is configured in `vite.config.ts`) and served by a multi-stage
   [frontend/Dockerfile] that builds with Bun and runs `bun build/index.js` as a non-root user
   with a `$PORT`-aware `HEALTHCHECK` for zero-downtime traffic switching. All backend calls go
   through the same-origin proxy route `/api/mh/[...path]` (`frontend/src/routes/api/mh/[...path]/+server.ts`),
   so the browser never needs CORS. The `(app)` route group sets `ssr = false` (the audio player
   reads browser-only state) while the marketing `/` route keeps SSR.
2. **Mobile is a shell, not a client.** `mobile/` is a Capacitor project (`@capacitor/core` 8,
   [mobile/capacitor.config.ts]) whose web view loads **the deployed frontend** of the server the
   user connects it to. It ships no pages of its own: the one bundled page
   (`mobile/www/index.html`) asks for the server address and doubles as the "can't reach" page,
   and the account menu offers "Change server" inside the app (`ShellServer` plugin). What it
   adds is `mobile/plugin` — one audio plugin in two implementations (Swift `AVQueuePlayer` /
   Android Media3 `ExoPlayer`) that holds the loaded track plus the next 20, so a song's end
   needs nothing from the page: the one thing a web page cannot do reliably on a locked phone.
   A page change reaches installed apps with the next deploy, with no app release.

To prevent the two-layer split from re-creating the drift it replaces, rules that two clients
could disagree about (album grouping, radio ranking, playback sync) live **on the server**
(`Library/AlbumProjection.cs`, `Library/RadioRanker.cs`, `Playback/PlaybackCoordinator.cs`), and
`#lib/native/` plus the two plugins form a versioned protocol: add methods, never rename or
remove, and a page must still work when it meets an older build.

## Options considered

| Dimension                          | SvelteKit adapter-node + Capacitor shell       | Static SPA adapter (no server)          | Native iOS + Android clients (the old `android/`) | React Native / Flutter cross-platform client |
| ---------------------------------- | ---------------------------------------------- | --------------------------------------- | --------------------------------------------------- | -------------------------------------------- |
| Same-origin API proxy, no CORS     | Yes (`/api/mh/[...path]`)                      | No — needs CORS or a separate gateway   | Native HTTP, no CORS issue                          | No CORS issue                                |
| SSR for share pages / og-tags      | Yes (landing + share routes)                   | No                                      | N/A                                                 | N/A                                          |
| Background/lock-screen playback    | Via the native audio plugin                    | Web Audio limitations on iOS            | Full native control                                 | Native modules                               |
| Rule duplication across clients    | None — one codebase; server-side rules         | None                                    | Every rule twice (observed: PR #453, six drifts)    | Every rule twice (JS/native bridge)          |
| Update path for fixes              | Deploy frontend; installed shells pick it up instantly | Same                            | App-store review per fix, per platform              | App-store review per fix                     |
| Store presence (Google Play, TestFlight) | Shell publishes under the retired client's application id | Not installable as an app | Full                                       | Full                                         |
| Effort                             | One web team; ~2 native plugins to maintain    | Lowest                                  | Highest                                             | High                                         |

## Trade-off analysis

- **Gained:** every bug fix and page change reaches all installed apps on the next deploy; one
  set of product rules; phone UX is still native where it matters (lock screen, widgets,
  background audio) without owning a second data layer.
- **Paid:** a protocol constraint — an installed app keeps the native half it was built with
  while its pages move on, so `#lib/native/` and the plugins must stay compatible with shipped
  builds forever. Stream authorization rides the web view's session cookie, and iOS-specific
  quirks (audio session lapsing, cookie jars separated from Safari, status-bar geometry) are
  absorbed with documented workarounds in `frontend/` and `mobile/` (see [AGENTS.md], the
  `frontend/` and `mobile/` sections).
- **Paid (deployment):** adapter-node means a running Node-compatible process per instance — one
  more container than a static adapter would need (see [ADR-001] for how it is orchestrated).

## Consequences

- The single-client rule is normative: [AGENTS.md] directs that new list/ranking rules belong on
  the server so a future client cannot drift.
- A change to `#lib/native/shell` / `native-audio.ts` / the two plugins is a three-way protocol
  change; change all three together.
- Store declarations in `mobile/store/README.md` describe the code; certain kinds of changes
  require checking that file's "When a change touches the declarations" table.
