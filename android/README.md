# MusicHoarder for Android

A native client for a self-hosted MusicHoarder deployment. This first version is a player: pair the
phone with your server, browse the library by song or album, and play it — in the background, with
lock-screen and Bluetooth controls.

## Requirements

- Android Studio (Otter or newer) — the project uses AGP 9 with built-in Kotlin support.
- A device or emulator on Android 7.0 (API 24) or newer.
- A running MusicHoarder deployment you can reach from the phone.

## Build and run

```bash
cd android && ./gradlew :app:assembleDebug
```

Install on a connected device:

```bash
cd android && ./gradlew :app:installDebug
```

`local.properties` (the SDK path) is generated by Android Studio and stays out of version control.

## Pairing

The app never asks for your email or a password. It takes a bearer token that the web UI mints:

1. Open MusicHoarder in a browser and sign in as the owner.
2. Go to **Settings → Account → Mobile app** and press **Show pairing code**.
3. In the app, press **Scan pairing code** and point the camera at it.

The QR encodes `musichoarder://pair?v=1&url=<origin>&token=<bearer token>`. `url` is the **frontend**
origin, not the API's: the SvelteKit app proxies `/api/mh/*` to the API and forwards the
Authorization header, so the phone needs exactly one reachable host — the same one the browser uses.
Nothing extra has to be exposed for mobile.

If the phone has no camera, or Play services cannot supply the scanner module, **Enter details
manually** takes the same server address and token — the pairing card has a "Can't scan?" section
that shows both in copyable form.

The token rides its own server-side session, so signing the browser out leaves the phone paired.
**Sign out everywhere** in the web UI revokes it; so does **Unpair** (the sign-out icon in the app's
toolbar). If the server rejects the token, the app returns to the pairing screen and says why.

### Local development

Point the app at a frontend dev server rather than the Aspire HTTPS endpoint, whose development
certificate Android will not trust:

```bash
cd frontend && MUSICHOARDER_API_URL=http://localhost:<api-port> bun run dev --port 3000
```

Over USB, `adb reverse tcp:3000 tcp:3000` makes `http://localhost:3000` on the phone resolve to that
server. Cleartext HTTP is permitted (see `res/xml/network_security_config.xml`) because plenty of
self-hosted instances live on a LAN without a certificate — prefer HTTPS wherever a reverse proxy
makes it possible, since the bearer token rides every request.

## How it is put together

```
data/     ServerSession (pairing + DataStore), MusicHoarderApi (OkHttp + kotlinx.serialization),
          LibraryRepository (the library, held in memory), Track/Album models
player/   PlaybackService (Media3 MediaSessionService), PlayerController (MediaController + UI state)
ui/       PairScreen, LibraryScreen, AlbumScreen, NowPlaying (mini + full player), AppViewModel
AppGraph  One OkHttpClient shared by the API, ExoPlayer, and Coil — so all three carry the token
```

Notable choices:

- **One HTTP client.** The bearer token is attached by a *network* interceptor that checks the host
  on every redirect hop, so a redirect to an external CDN cannot carry the credential off-server.
- **The list you see is the queue you get.** Tapping a row queues everything visible below it, the
  same contract as the web player.
- **`GET /songs` is a whole-library dump**, fetched once per app start (the web app does the same).
  A paged or delta endpoint is the obvious next step for very large libraries.
